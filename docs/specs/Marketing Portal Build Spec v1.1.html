Marketing Portal — Front-end Build Spec v1.1

For the Next.js developer building the marketing portal. The AI engine, Pexels photos and publishing to each site's website (WordPress or Strapi, through a per-CMS adapter) are built on our side and exposed through the API below. You build the screens and call this API. You never call WordPress, Strapi, Pexels, LinkedIn, Instagram or Google Search Console directly.

0. What changed in v1.1

v1.1 is the agreed contract between the portal and the engine. Both sides build against it. The portal is built against a mock of these shapes until the engine is live.

Changes

  • Website connection replaces Strapi-only publishing. StrapiSettings becomes PublishTarget with type: "wordpress" | "strapi", and the settings form is described by /meta.targetTypes. The following endpoints and fields are renamed:
    • /settings/strapi → /settings/website
    • /strapi/categories → /website/categories
    • connections.strapi → connections.website
    • the connection.changed type strapi → website
    Post.published gains target and externalId (§4, §11).
  • One portal deployment per site. A key reaches one site, so the site switcher is removed. Routes no longer need a /sites/[siteId] prefix (§6).
  • Idempotency. Every POST/PUT/DELETE carries an Idempotency-Key. A repeat within 24 hours returns the original result, so a retried click can't publish twice (§3).
  • Feature flags. /meta.features lists the optional features this engine supports. The portal shows their screens and buttons only when they're listed (§12).
  • Locking is specified. POST/DELETE …/posts/{id}/lock, plus lockedBy and lockedAt on Post (§3, §4).
  • Arabic twins mirror the English structure, which TranslatePress requires. On TranslatePress sites, a mismatch is a critical, non-overridable finding with code structure_mismatch (§11).
  • Four extras (§12): import your own article; article → social posts; search performance (Google Search Console); legal accuracy & internal linking.
  • Corrections to v1:
    • createdAt, updatedAt and version were inside a comment in Post; they're now real fields.
    • error.details is part of the error envelope.
    • The "wizard" acceptance line is reworded as a website-connection test.
    • profile is removed from PUT /sites/{id}; the profile lives in SeoSettings.
    • Suggestions gain the status drafted.
    • The keyword restore action gets a button.
    • Instagram posts require an image.
    • Usage and results are for this site only.
Questions for Quantum1st before sign-off:
  1. Is the engine live? Please send the real base URL, a sandbox key, and an estimated timeline.
  2. Please send the article-checks rulebook that findings cite (ref values such as §4.6.1).
  3. Please confirm the 24-hour idempotency window and the lock duration (/meta.limits.lockMinutes).

1. Overview

  • Account: one client company. It has users and one or more Sites.
  • Site: one website. Each site has its own website connection (WordPress or Strapi), SEO settings, keywords, articles, social channels and publishing schedule. Each site can be in any category, not just legal. A site can switch its website connection to another CMS later.
  • Our engine proposes keywords and topics, writes articles and social posts, finds photos (Pexels), checks SEO, publishes to the site's website through the matching CMS adapter (§11), and posts to connected social channels.
  • Your portal covers review, approval, scheduling, settings and history. One portal deployment serves one site, with one key. Every call is scoped to that site: /api/v1/sites/{siteId}/….
Keywords ─► Suggestions (topics) ─► Draft (async job) ─► Review ─► Approve ─► Scheduled queue ─► Published (website / social) │ │ └ changes ◄──┘ reject / delete

2. Ground rules

  • No hard-coded values in the UI. Lists (languages, platforms, website categories, website connection types and their fields, statuses, limits such as photo size) come from GET /meta or from site settings. Never put the numbers in the code.
  • Optional features follow /meta.features. A screen or button for an extra (§12) appears only when its feature is listed. No redeploy is needed when we switch one on.
  • Every change is idempotent. Send a fresh Idempotency-Key per user action. If no response arrived (network error or timeout), retry with the same key. After a definite error response, a new attempt uses a new key.
  • Every page uses its data. Each page below lists the exact endpoints it calls. Don't add pages, fields or buttons that aren't wired to an endpoint.
  • Drafting is async. Anything that writes with AI returns a jobId. Show progress, then refresh from the webhook or by polling GET /jobs/{id}.
  • Nothing goes live without a person, unless the site has auto-publish turned on. Even then, only articles already approved get published.
  • Show errors as text. Every error comes back with a readable message. Show it as it is.
  • Use the times we send. Times are ISO 8601 with offset. Display them in 12-hour AM/PM in the site's timezone (site.timezone).
  • RTL. Content in ar renders right to left: the editor, the preview and the cards.

3. API conventions

Base URL and auth

Base:    https://api.<our-domain>/api/v1
Auth:    X-Api-Key: <this site's key>          (one key per site, issued by Quantum1st)
         X-Acting-User: <name or email>       (who in your app did it, kept in our audit log; required on every change)
         Idempotency-Key: <uuid>              (required on POST/PUT/DELETE; a repeat within 24h returns the original result)
Content: application/json; charset=utf-8   (photo and article upload: multipart/form-data)

Each site's app has its own key. A key reaches only its own site: any other siteId returns 404.

  • Call the API only from the server side (Next.js server actions or route handlers). Keep the key in a server environment variable, never in the browser.
  • Your app runs its own login for its users. We don't hold any user accounts or passwords.
  • Pass the signed-in person in X-Acting-User.

Response envelope

// success
{ "ok": true, "data": { ... }, "meta": { "page": 1, "pageSize": 25, "total": 140 } }
// error
{ "ok": false, "error": { "code": "framework_blocked", "message": "Not approved — 2 framework rules to fix.",
                          "fields": { "meta_description": "Too long" }?,      // per-field messages (400 invalid_input)
                          "details": { ... }? } }                            // code-specific data, e.g. 429: {metric,used,limit}

Lists

Query params: ?page=1&pageSize=25&status=pending&language=en&q=search&sort=-updated_at. pageSize has a server-side maximum, returned in GET /meta.

Bulk actions

POST …/bulk   { "action": "approve", "ids": ["p_1","p_2"], "note": "optional" }
→ { "ok": true, "data": { "done": ["p_1"], "failed": [ { "id": "p_2", "code": "framework_blocked", "message": "…" } ] } }

Async jobs

POST …/drafts  →  202 { "ok": true, "data": { "jobId": "j_9f2", "status": "queued", "postIds": ["p_77"] } }
GET  /jobs/j_9f2 → { "ok": true, "data": { "id": "j_9f2", "status": "running|done|failed", "progress": 0.6, "result": {...}, "error": null } }

IDs, dates, concurrency

  • IDs are strings with a prefix (site_, p_, kw_, sg_, j_). Treat them as opaque.
  • Every editable object has a version. Send it back on PUT. A 409 version_conflict means someone else saved first: reload and show both versions.

Editing locks

  • Opening a post in the editor calls POST …/posts/{id}/lock. The lock lasts /meta.limits.lockMinutes, and calling the same endpoint while editing renews it.
  • Leaving the editor calls DELETE …/posts/{id}/lock. An expired lock is released automatically.
  • While another person holds the lock, PUT and actions return 409 locked, with error.details = {lockedBy, lockedAt}. POST …/posts/{id}/takeover moves the lock to the caller.
  • Post.lock shows the current holder (§4).

Finding (check result)

{ "level": "critical|warn|human", "code": "alt_length"?, "ref": "§4.6.1", "overridable": true,
  "message": "the image alt text is 4 words; the band is 8–14" }

code is a stable machine name (for example structure_mismatch, citation_unverified). ref points into the article-checks rulebook. Show message as it is.

  • warn is shown but does not block.
  • human is a checklist item for the reviewer. It is never shown as passed.

5. Status flows

Post

drafting ──(job done)──► pending ──approve──► approved ──(queue / publish now)──► published ▲ │ │ │ └──── changes (note) ─────┘ └──reject──► rejected└──(publish error)──► failed ──retry──► approved delete: any status except published

A critical structure_mismatch finding (TranslatePress sites, §11) blocks approval and publishing and can't be overridden. Approving or publishing one language never changes its twin.

Keyword

new ──approve──► approved (in use) ──(article published)──► covered └─dismiss──► dismissed ──restore──► new └─(AI: outside site strategy)──► off_strategy

Suggestion

new ──draft──► drafting ──(job done)──► drafted └─dismiss──► dismissed

The buttons on a card depend on its status. Use post.actions, an array returned by the API such as ["approve","changes","reject","edit","publishNow"], instead of working the rules out in the browser.

6. Pages

Routes for the App Router. One portal deployment serves one site, so there is no site switcher and routes don't need a /sites/[siteId] prefix. The portal reads the siteId once from GET /sites (this key's one site) on the server. The route names below are suggestions.

/sign-in (your own)

Your app's own sign-in for the site's team. It makes no call to our API. After sign-in, open the dashboard.

First-run setup (no page of its own)

Quantum1st creates the site and its key. When your app first opens and connections.website.status is missing, send the user to /settings/website and then to /settings/social.

Calls: GET /sites, GET /sites/{id}.

/ (dashboard)

Counts: suggestions, waiting for review, scheduled, published this month, failed. Also shows the next publish slot, and connection warnings (a token expiring, or the website connection down) that link to settings.

Also shows quota bars for the account (from GET /account/plan) and this site's share of the usage.

Calls: GET /sites/{id}, GET /sites/{id}/scheduled?pageSize=5, GET /account/plan.

/keywords

Tabs:

  • New: proposed keywords.
  • In use: approved. Every new draft is written with these.
  • Covered: a published article carries the keyword.
  • Dismissed.

A table shows the phrase, language, source, rationale and uses. Buttons:

  • Add keyword(s): comma or line separated.
  • Approve or dismiss the selected keywords. On the Dismissed tab, Restore moves them back to New.
  • Propose keywords (AI): starts a job.
  • Propose topics for selected: starts a job.
  • Draft articles for selected: one article per keyword, starts a job, and asks for confirmation first.

Calls: GET /keywords?status=, POST /keywords, POST /keywords/bulk, POST /keywords/propose, POST /keywords/topics, POST /keywords/draft-articles.

/suggestions

Cards show title, type, language, keywords and why. Actions: Draft, with a choice of language (en, ar or both), or Dismiss. Bulk versions of both. A drafted suggestion links to its drafts (postIds).

A New request form takes topic, type (blog/social), platform, language (en, ar or both), tone and optional keywords. If keywords are left empty, the server proposes them.

Calls: GET /suggestions, POST /suggestions/{id}/draft, POST /suggestions/{id}/dismiss, POST /suggestions/bulk, POST /drafts.

/review

Posts with status drafting or pending. While drafting, a card shows a spinner. Each card shows the title, language, a twin badge (for a language pair), counts of critical and warn findings, and its photo. Bulk approve and bulk publish now are available.

If a bulk approve includes a post with a critical finding, those posts fail and are listed by name. Overriding a critical finding is a per-article decision, so it is never done in bulk.

Calls: GET /posts?status=drafting,pending, POST /posts/bulk.

/review/[postId] (editor)

Opening the editor takes the lock (§3) and renews it while editing. If someone else holds it, the editor shows "Being edited by X" with Take over. For a language pair, a side-by-side view shows the twin next to this post, section by section.

Left side, the fields:

  • Title.
  • Standfirst.
  • Body: a rich text editor that outputs HTML.
  • Slug.
  • Meta title and meta description, each with a live character count. The limits come from /meta.
  • Keywords: chips, the first one is the focus keyword.
  • Section: a dropdown filled from GET /website/categories.
  • Hashtags: social posts only.

Right side:

  • Photo panel:
    • The suggested search (photoIdea) with a Find a photo button that opens a Pexels grid.
    • Upload. Allowed types and maximum size come from /meta.
    • Remove.
    • Alt text and credit fields.
  • Checks panel: findings grouped as critical, warn and human, plus the SEO score.
  • Sources list. With feature legalChecks, it also lists linkSuggestions (internal links), each with an Insert button.

Footer buttons:

  • Save.
  • Approve. If there are critical findings, an override reason box appears.
  • Ask for changes, with a note. The post is redrafted and comes back.
  • Reject.
  • Delete.
  • Publish now, after a confirmation.
  • Export HTML or Markdown.
  • Create social posts (feature repurpose; approved or published articles only).

Calls: GET/PUT /posts/{id}, POST/DELETE /posts/{id}/lock, POST /posts/{id}/takeover, GET /posts/{id}/seo-check, GET /photos/search?q=, POST /posts/{id}/image (multipart), POST /posts/{id}/image/pick, DELETE /posts/{id}/image, POST /posts/{id}/approve|changes|reject|publish, DELETE /posts/{id}, GET /posts/{id}/export.html|md, GET /website/categories, POST /posts/{id}/repurpose.

/scheduled

Approved posts in queue order. Each shows its position, expected time, and whether it is on hold. A banner shows the auto-publish state and the next slot, or the reason nothing is going out (outside hours, daily limit reached, waiting for the gap, queue empty).

Actions: Hold or Resume, Publish now (single or bulk). Publishing now does not use up the day's allowance.

Calls: GET /scheduled, POST /posts/{id}/hold, POST /posts/{id}/publish, POST /posts/bulk {action:"publishNow"}.

/history

Published, failed and rejected posts. Each shows its live URL, publish time, platform, target (WordPress, Strapi or social), any override reason and error text. Failed posts have a Retry button. With feature repurpose, published articles have Create social posts.

Calls: GET /posts?status=published,failed,rejected, POST /posts/{id}/publish.

/site-health

Buttons: Scan site (starts a job) and Prepare fixes for selected findings. A findings table shows URL, level, issue, proposed fix and status. Apply and dismiss work per finding.

Calls: POST /site/scan, GET /site/findings, POST /site/fixes, POST /site/findings/bulk.

/settings/seo · /publishing · /website · /social

One form for each model in section 4.

  • SEO includes a share image upload.
  • Publishing has an on/off toggle, per day, days, from/to times and gap in minutes.
  • Website (replaces Strapi):
    • A type picker from /meta.targetTypes.
    • The fields for that type, drawn from the type's fields, including a write-only secret.
    • The field map editor (simple fields).
    • Body format (from bodyFormats) and, for Strapi, the block map.
    • Arabic mode (from arabicModes).
    • Test connection, which pre-fills the field map and block map from the test result. Saving is blocked while the test fails.
  • Social has a Connect or Reconnect button per platform (OAuth redirect) and shows token expiry. With feature performance, it also offers Google Search Console.

Calls: GET/PUT /settings/seo, POST /settings/seo/propose (AI suggests focus keywords and CTA), POST/DELETE /settings/seo/picture, GET/PUT /settings/publishing, GET/PUT /settings/website, POST /settings/website/test, GET /settings/social, GET /settings/social/{platform}/connect, DELETE /settings/social/{platform}, GET /settings/search-console/connect, DELETE /settings/search-console.

10. Acceptance checklist

  • Every page loads real data from the API, with no mocked lists left behind.
  • Saving a website connection with a wrong WordPress application password or Strapi token shows the test error message and the save is blocked.
  • The website settings form is drawn entirely from /meta.targetTypes. Switching between WordPress and Strapi needs no portal code change.
  • Publishing the same post twice through a repeated Idempotency-Key (simulated timeout) produces one publication, not two.
  • On a TranslatePress site, an Arabic twin with a structure_mismatch finding can't be approved or published, even with an override reason. The side-by-side view shows where the two versions differ.
  • Screens and buttons for extras appear only when /meta.features lists them.
  • Opening a post someone else is editing shows "Being edited by X". Take over works, and the lock is released on leaving the editor.
  • Drafting in "both" languages creates two linked posts. Approving one does not approve the other.
  • Approving a post with a critical finding is refused. With an override reason it goes through, and the reason shows in History.
  • Picking a Pexels photo saves the credit. Uploading a file of the wrong type shows the server's message.

11. Website adapters (built on our side)

The engine stores every article in one neutral form: title, standfirst, headings, paragraphs, lists, FAQ, tables, quotes, images, SEO fields and language. On publish, the adapter for the site's PublishTarget.type converts it. The portal never sees adapter details beyond the settings in §4 and /meta.targetTypes.

WordPress adapter

  • Auth: a WordPress Application Password for a dedicated user with the Editor role, never an administrator. Security plugins may disable application passwords (Wordfence does by default), so the test reports that case with a clear message.
  • Publishing:
    • Create and update posts through /wp-json/wp/v2/posts (or the configured post type).
    • Upload images through /wp/v2/media and set the featured image.
    • Categories come from /wp/v2/categories.
    • A refresh (§12) updates the same post ID.
  • Body format: html (clean semantic HTML) or boldbuilder (Bold Builder shortcodes, for themes that style only builder content).
  • Helper plugin (ours, installed on the site): the standard REST API can't do two things, so the plugin does them:
    1. Write the Yoast SEO title and meta description, and focus keyphrase if present.
    2. With arabic.mode = translatepress, store the Arabic twin as the TranslatePress translation of the English post, served at /ar/<slug>/, instead of creating a second post.
    The plugin authenticates with the same application password and exposes only these two operations.
  • arabic.mode = separate: the Arabic twin is published as its own post. Use this only on sites without a translation plugin.

Strapi adapter

  • Auth: a Strapi API token with create, update and upload rights on the configured collection.
  • Body: converted to the collection's dynamic-zone blocks using body.blockMap. Block names differ per Strapi, so …/settings/website/test reads the content-type schema and returns blockTypes and suggestedBlockMap.
  • SEO, images, categories: mapped through fieldMap. These fields may be components (e.g. seo.metaTitle), media or relations.
  • Arabic: published as the ar locale of the same document (arabic.mode = locale).

Rules for both adapters

  • Matching structure. When drafting in both languages, the engine produces an Arabic twin with the same structure as the English: the same headings, paragraphs, list items, FAQ items and tables, in the same order. TranslatePress pairs strings by position, so with arabic.mode = translatepress a twin that doesn't match gets a critical finding with code: "structure_mismatch". This finding can't be overridden: publishing it would scramble the translation. Fix it by editing either version or with Ask for changes. In the other modes, the same check is a warn.
  • Switching CMS. When a site switches type, posts that are already published keep published.target, url and externalId. New publishes go to the new target. Moving old articles is a separate migration, not part of this API.
  • Errors. Adapter failures return 502 publish_failed, with a message the reviewer can understand (for example "WordPress refused: application passwords are disabled on this site").

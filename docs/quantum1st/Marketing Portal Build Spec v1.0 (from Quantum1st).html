Marketing Portal — Front-end Build Spec

For the Next.js developer building the multi-site marketing portal. The AI engine, Pexels photos and Strapi publishing already exist on our side and are exposed through the API below. You build the screens and call this API. You never call Strapi, Pexels, LinkedIn or Instagram directly.

API v1React · Next.js App RouterJSON over HTTPSQuantum1st

1. Overview

  • Account: one client company. It has users and one or more Sites.
  • Site: one website. Each site has its own Strapi, SEO settings, keywords, articles, social channels and publishing schedule. Each site can be in any category, not just legal.
  • Our engine proposes keywords and topics, writes articles and social posts, finds photos (Pexels), checks SEO, publishes to the site's Strapi and posts to connected social channels.
  • Your portal covers onboarding, review, approval, scheduling, settings and history. Every call is scoped to one site: /api/v1/sites/{siteId}/….
Keywords ─► Suggestions (topics) ─► Draft (async job) ─► Review ─► Approve ─► Scheduled queue ─► Published (Strapi / social) │ │ └ changes ◄──┘ reject / delete

2. Ground rules

  • No hard-coded values in the UI. Lists (languages, platforms, Strapi sections, statuses, limits such as photo size) come from GET /meta or from site settings. Never put the numbers in the code.
  • Every page uses its data. Each page below lists the exact endpoints it calls. Don't add pages, fields or buttons that aren't wired to an endpoint.
  • Drafting is async. Anything that writes with AI returns a jobId. Show progress, then refresh from the webhook or by polling GET /jobs/{id}.
  • Nothing goes live without a person, unless the site has auto-publish turned on. Even then, only articles already approved get published.
  • Show errors as text. Every error comes back with a readable message. Show it as it is.
  • Use the times we send. Times are ISO 8601 with offset. Display them in 12-hour AM/PM in the site's timezone (site.timezone).
  • RTL. Content in ar renders right to left: the editor, the preview and the cards.

3. API conventions

Base URL and auth

Base:    https://api.<our-domain>/api/v1
Auth:    X-Api-Key: <this site's key>          (one key per site, issued by Quantum1st)
         X-Acting-User: <name or email>       (optional: who in your app did it, kept in our audit log)
Content: application/json; charset=utf-8   (photo upload: multipart/form-data)

Each site's app has its own key. A key reaches only its own site: any other siteId returns 404.

  • Call the API only from the server side (Next.js server actions or route handlers). Keep the key in a server environment variable, never in the browser.
  • Your app runs its own login for its users. We don't hold any user accounts or passwords.
  • Pass the signed-in person in X-Acting-User.

Response envelope

// success
{ "ok": true, "data": { ... }, "meta": { "page": 1, "pageSize": 25, "total": 140 } }
// error
{ "ok": false, "error": { "code": "framework_blocked", "message": "Not approved — 2 framework rules to fix.", "fields": { "meta_description": "Too long" } } }

Lists

Query params: ?page=1&pageSize=25&status=pending&language=en&q=search&sort=-updated_at. pageSize has a server-side maximum, returned in GET /meta.

Bulk actions

POST …/bulk   { "action": "approve", "ids": ["p_1","p_2"], "note": "optional" }
→ { "ok": true, "data": { "done": ["p_1"], "failed": [ { "id": "p_2", "code": "framework_blocked", "message": "…" } ] } }

Async jobs

POST …/drafts  →  202 { "ok": true, "data": { "jobId": "j_9f2", "status": "queued", "postIds": ["p_77"] } }
GET  /jobs/j_9f2 → { "ok": true, "data": { "id": "j_9f2", "status": "running|done|failed", "progress": 0.6, "result": {...}, "error": null } }

IDs, dates, concurrency

  • IDs are strings with a prefix (site_, p_, kw_, sg_, j_). Treat them as opaque.
  • Every editable object has a version. Send it back on PUT. A 409 version_conflict means someone else saved first: reload and show both versions.

5. Status flows

Post

drafting ──(job done)──► pending ──approve──► approved ──(queue / publish now)──► published ▲ │ │ │ └──── changes (note) ─────┘ └──reject──► rejected└──(publish error)──► failed ──retry──► approved delete: any status except published

Keyword

new ──approve──► approved (in use) ──(article published)──► covered └─dismiss──► dismissed └─(AI: outside site strategy)──► off_strategy

The buttons on a card depend on its status. Use post.actions, an array returned by the API such as ["approve","changes","reject","edit","publishNow"], instead of working the rules out in the browser.

6. Pages

Routes for the App Router. Every page under /sites/[siteId] has the site switcher in the layout.

/login (your own)

Your app's own sign-in for the site's team. It makes no call to our API. After sign-in, open /sites/[siteId]/dashboard. The siteId comes from GET /sites, which returns this key's one site.

First-run setup (no page of its own)

Quantum1st creates the site and its key. When your app first opens and connections.strapi is missing, send the user to /settings/strapi and then to /settings/social.

Calls: GET /sites, GET /sites/{id}.

/sites/[siteId]/dashboard

Counts: suggestions, waiting for review, scheduled, published this month, failed. Also shows the next publish slot, and connection warnings (a token expiring or Strapi down) that link to settings.

Also shows quota bars for the account (from GET /account/plan) and this site's share of the usage.

Calls: GET /sites/{id}, GET /sites/{id}/scheduled?pageSize=5, GET /account/plan.

/sites/[siteId]/keywords

Tabs:

  • New: proposed keywords.
  • In use: approved. Every new draft is written with these.
  • Covered: a published article carries the keyword.
  • Dismissed.

A table shows the phrase, language, source, rationale and uses. Buttons:

  • Add keyword(s): comma or line separated.
  • Approve or dismiss the selected keywords.
  • Propose keywords (AI): starts a job.
  • Propose topics for selected: starts a job.
  • Draft articles for selected: one article per keyword, starts a job, and asks for confirmation first.

Calls: GET /keywords?status=, POST /keywords, POST /keywords/bulk, POST /keywords/propose, POST /keywords/topics, POST /keywords/draft-articles.

/sites/[siteId]/suggestions

Cards show title, type, language, keywords and why. Actions: Draft, with a choice of language (en, ar or both), or Dismiss. Bulk versions of both.

A New request form takes topic, type (blog/social), platform, language (en, ar or both), tone and optional keywords. If keywords are left empty, the server proposes them.

Calls: GET /suggestions, POST /suggestions/{id}/draft, POST /suggestions/{id}/dismiss, POST /suggestions/bulk, POST /drafts.

/sites/[siteId]/review

Posts with status drafting or pending. While drafting, a card shows a spinner. Each card shows the title, language, a twin badge (for a language pair), counts of critical and warn findings, and its photo. Bulk approve and bulk publish now are available.

If a bulk approve includes a post with a critical finding, those posts fail and are listed by name. Overriding a critical finding is a per-article decision, so it is never done in bulk.

Calls: GET /posts?status=drafting,pending, POST /posts/bulk.

/sites/[siteId]/review/[postId] (editor)

Left side, the fields:

  • Title.
  • Standfirst.
  • Body: a rich text editor that outputs HTML.
  • Slug.
  • Meta title and meta description, each with a live character count. The limits come from /meta.
  • Keywords: chips, the first one is the focus keyword.
  • Section: a dropdown filled from GET /strapi/categories.
  • Hashtags: social posts only.

Right side:

  • Photo panel:
    • The suggested search (photoIdea) with a Find a photo button that opens a Pexels grid.
    • Upload. Allowed types and maximum size come from /meta.
    • Remove.
    • Alt text and credit fields.
  • Checks panel: findings grouped as critical, warn and human, plus the SEO score.
  • Sources list.

Footer buttons:

  • Save.
  • Approve. If there are critical findings, an override reason box appears.
  • Ask for changes, with a note. The post is redrafted and comes back.
  • Reject.
  • Delete.
  • Publish now, after a confirmation.
  • Export HTML or Markdown.

Calls: GET/PUT /posts/{id}, GET /posts/{id}/seo-check, GET /photos/search?q=, POST /posts/{id}/image (multipart), POST /posts/{id}/image/pick, DELETE /posts/{id}/image, POST /posts/{id}/approve|changes|reject|publish, DELETE /posts/{id}, GET /posts/{id}/export.html|md, GET /strapi/categories.

/sites/[siteId]/scheduled

Approved posts in queue order. Each shows its position, expected time, and whether it is on hold. A banner shows the auto-publish state and the next slot, or the reason nothing is going out (outside hours, daily limit reached, waiting for the gap, queue empty).

Actions: Hold or Resume, Publish now (single or bulk). Publishing now does not use up the day's allowance.

Calls: GET /scheduled, POST /posts/{id}/hold, POST /posts/{id}/publish, POST /posts/bulk {action:"publishNow"}.

/sites/[siteId]/history

Published and failed posts. Each shows its live URL, publish time, platform and error text. Failed posts have a Retry button.

Calls: GET /posts?status=published,failed,rejected, POST /posts/{id}/publish.

/sites/[siteId]/site-health

Buttons: Scan site (starts a job) and Prepare fixes for selected findings. A findings table shows URL, level, issue, proposed fix and status. Apply and dismiss work per finding.

Calls: POST /site/scan, GET /site/findings, POST /site/fixes, POST /site/findings/bulk.

/sites/[siteId]/settings/seo · /publishing · /strapi · /social

One form for each model in section 4.

  • SEO includes a share image upload.
  • Publishing has an on/off toggle, per day, days, from/to times and gap in minutes.
  • Strapi has a write-only token field, the field map editor, and Test connection.
  • Social has a Connect or Reconnect button per platform (OAuth redirect) and shows token expiry.

Calls: GET/PUT /settings/seo, POST /settings/seo/propose (AI suggests focus keywords and CTA), POST/DELETE /settings/seo/picture, GET/PUT /settings/publishing, GET/PUT /settings/strapi, POST /settings/strapi/test, GET /settings/social, GET /settings/social/{platform}/connect, DELETE /settings/social/{platform}.

/account

Webhook URL setup. Your app manages its own users and roles. We never see them.

Plan & usage tab:

  • Plan name and period.
  • Quota bars.
  • Usage per site and per metric, with a monthly chart covering the last months.
  • Results per site: articles published, keywords covered, live URLs.
  • A "Request upgrade" button.

Calls: GET /account/plan, GET /account/usage, POST /account/upgrade-request, GET/PUT /sites/{id}/webhook.

8. Webhooks (we → your portal)

The portal exposes one HTTPS endpoint, for example POST /api/hooks/marketing, and registers it with PUT /sites/{siteId}/webhook (one webhook per site app). We sign every call so you can verify it came from us.

Headers:  X-Signature: sha256=<HMAC of raw body with this site's webhook secret>
          X-Event-Id: evt_…      (deliveries are retried; ignore an id you have already seen)
Body:     { "event": "post.drafted", "siteId": "site_12", "at": "2026-10-20T18:40:00+04:00", "data": { ... } }
EventdataPortal action
job.finished{jobId,status,result?,error?}Stop the spinner and refresh the list
post.drafted{postId,status:"pending"}Show the post in Review and notify reviewers
post.published{postId,url,platform}Move it to History
post.failed{postId,error}Show the error and offer Retry
suggestions.created{ids}Update the Suggestions badge
keywords.proposed{ids}Update the Keywords "New" badge
connection.changed{type:"strapi|linkedin|instagram",status,error?}Show a warning banner
site.scan_finished{findings:n}Refresh Site health
quota.warning{metric,used,limit}Show a banner: near the limit
quota.exceeded{metric,used,limit,mode}Banner, and disable the related buttons if the mode is hard
plan.changed{planId}Reload /account/plan

If no webhook is set, poll GET /jobs/{id} every few seconds while a job is open. The poll interval is returned in /meta.

10. Acceptance checklist

  • Every page loads real data from the API, with no mocked lists left behind.
  • Creating a site with a wrong Strapi token shows the test error message and blocks the wizard.
  • Drafting in "both" languages creates two linked posts. Approving one does not approve the other.
  • Approving a post with a critical finding is refused. With an override reason it goes through, and the reason shows in History.
  • Picking a Pexels photo saves the credit. Uploading a file of the wrong type shows the server's message.
  • With auto-publish off, nothing leaves the Scheduled page until someone presses Publish now.
  • Arabic posts render right to left in the editor, the preview and the cards.
  • All times show in 12-hour AM/PM in the site's timezone.
  • The webhook handler rejects a request with a wrong signature and ignores a repeated X-Event-Id.
  • The API key never reaches the browser: check the network tab, where only your own app's routes appear.
  • Every call that changes something sends X-Acting-User.
  • When a hard quota is reached, drafting is refused with the 429 message and the Request upgrade button shows. Quota bars match /account/plan.
  • No quota numbers or metric names are hard-coded in the UI. All come from /account/plan.
Built on our side, not by you: plans, quotas, usage metering and the admin analytics; the multi-site API, per-site Strapi and social tokens, the Pexels search, the AI engine, and the article checks (which become per-site rules).
